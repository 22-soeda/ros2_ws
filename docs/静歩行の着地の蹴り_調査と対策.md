# 静歩行の着地で床を蹴る — 調査と対策（2026-09-18）

静歩行（`walk_mode:=static`）で遊脚を下ろすとき、足が床を蹴って機体が傾く。その原因を
bag から突き止め、対策を 2 つ入れたところまでの記録。**実機での効果確認は途中**。

関係するコミット: `09b7d07`（板の足裏補正）、`708b6c5`（押し込みの撤廃）。

---

## まとめ

| | 調査前 | 今 |
|---|---|---|
| 指令が狙う遊脚の高さ（振り出しの終わり、支持足の足裏から） | **−12.6mm** | **+0.2mm** |
| うち歩行計画（`td_overdrive`）の分 | −4.0mm | 0（撤廃） |
| うち安定化の補正の分 | −9mm（悪い歩で −20mm） | 0（板にして構造的に消えた） |
| 実測（エンコーダ + FK）の食い違い | −9.6mm | −2.6mm（まっすぐ立っている歩は **0**） |

**指令として床を押し込む分はゼロになった。** 残っているのは指令どおりに動けていない分で、
機体が傾いた歩でだけ 3〜7mm 出る。

---

## 1. 何が起きていたか

### 原因は 2 つ、大きいのは安定化のほう

1. **歩行計画の押し込み（−4mm）**: `static_gait.yaml` の `td_overdrive`。振り出しの位相 0.847 で
   支持足と同じ高さになり、そこから終わりまでに 4mm 下を狙う。その間も足は前へ約 2mm 進み、
   着地の次の周期で 0 に戻る（4mm の段差）。動歩行から引き継いだ設計。
2. **安定化の足首補正（−9mm、悪い歩で −20mm）**: 支持足首を回すと胴体ごと傾くのに、遊脚の目標は
   胴体を基準に作られたままなので、その傾きの分だけ遊脚が下がる。足間隔 140mm が腕になるので、
   ロール 4° で約 10mm。振り出しの終わりに、補正が遊脚側を下げる向きへ育っていた。

分解（bag `rosbag2_2026_09_18-02_40_03`、24 歩、位相 0.9 以降の平均。支持足の足裏を床とした遊脚の中心）:

| | 補正なしで計算 | 支持足の補正だけ | 両方 |
|---|---|---|---|
| 遊脚の高さ | −3.5mm | −12.6mm | −12.6mm |

**ずれは全部支持足の補正から来る。遊脚側の補正は足の中心の高さを変えない。**

### 調べ方（IMU は使わない）

`/motion/joint_commands`（指令の関節角）と `/joint_states`（実測の関節角）を
`ros2 run roboone_kinematics leg_service` の `fk` に通し、両脚の足裏の (p, R) を出す。
そのうえで **支持足の足裏を床（z = 0）とみなして**、遊脚の足裏 4 隅の高さを出す。

- IMU の rpy は**使わない**。人が支えたり持ったりした動きが混ざるため（ユーザ指摘）。
  両足で立っている IDLE でも roll が −1.2° 片寄り、SHIFT 中は −14〜+5° 振れていた。
- 見えないもの: 関節の外のたわみ（リンクのしなり・ガタ・足裏のつぶれ）。膝の電流と偏差で見ると、
  エンコーダ上はまだ 18mm 浮いている位相 0.6 で既に床に当たっている。
- 記録は 10Hz。実測は指令から約 0.1s 遅れる。足裏は 118 × 74mm、IK の目標点が中心という前提。

## 2. 入れた対策

### (a) 板の足裏補正 `stab.board`（`09b7d07`）

両足裏を 1 枚の板と見て、**2 足の中点（高さは低いほうの足裏 = 床）を軸に平面ごと回す**。

    p' = c + Q·(p − c)      R' = Q·R      Q = Ry(pitch)·Rx(roll)

2 足の相対位置と相対姿勢が変わらないので、遊脚が床へ押し込まれない。代わりに脚が
`(W/2)·sin u` ずつ伸び縮みする（4° で ±4.9mm）。支持足から見た胴体の傾き（＝立て直しの効き目）は
足首だけ回す従来の方式と同じ。

- 従来の方式も残してある。`ros2 param set /motion stab.board false` で戻せる（切り替えても跳ねない）。
- **`motion_node.yaml` の既定は板（`board: true`）**。
- 上限 `stab.board_clamp` = 0.07 rad（約 4°）。足首パラレルリンクが先に尽きるため
  （ロール単独なら 6° まで届くが、ロールとピッチが同時に入る隅は 4°。**歩幅には依らない**。
  60 → 15mm に詰めても変わらなかった）。
- 上限を超える周期は `PoseCodec` が **両脚まとめて** 75% → 50% → 25% → 0 と縮めて出す。
  片脚だけ外すと同じ平面に乗らなくなるため。縮めた割合は `/motion/stab` の `board_scale`。
- 起動時に `checkBoardEnvelope` が計画の全時刻 × 板の隅 8 通りを IK と機構層に通す
  （±4° で 静歩行 0.003% / 動歩行 2.5% が届かない。動歩行は計画そのものが到達域の縁にある）。
- 検算は `motion_selftest` の [8] (b2)(e2)。平面の保存・伸び縮みの量と符号・縮退・方式の切り替え。

### (b) 押し込みの撤廃 `td_overdrive` = 0（`708b6c5`）

`static_gait.yaml` を 0 にした。遊脚の z は振り出しの終わりにちょうど 0 に着き、接地の位相は
0.847 → **1.000**。着地の周期に 4mm 戻る段差も消えた。

「ちょうど 0 で着く」計画を浮動小数の丸めで「床に届かない」と弾かないよう、接地の判定に
1nm の許容を入れた（Python 原本と C++。JS に判定は無い）。これが無いと C++ の門だけエラーを出す。

**動歩行（`gait.yaml`）の `td_overdrive` 4mm と、コードの既定値 0.004 はそのまま。**
動歩行は遊脚が着く前に支持脚が入れ替わると危ないので、指示があるまで触らない。

## 3. 対策後の実測（bag `rosbag2_2026_09_18-04_00_45`、19 歩）

板と押し込み撤廃の**両方が入った状態**。`board_scale` は常に 1.0（一度も縮めていない）、
足首方式の補正は 0。

| | 指令 | 実測 |
|---|---|---|
| 振り出しの終わり（位相 0.9〜1.0 の平均） | **+0.2mm** | −2.6mm |
| 位相 0.8 以降の最小（歩ごとの最悪） | +0.0〜+0.1mm | −0.6 〜 **−7.0mm** |

歩ごとに見ると、傾きと連動している。

| 歩 | 胴体の \|roll\| 最大 | 実測の最下点 |
|---|---|---|
| 12〜17（94〜130s） | 0.6〜3.4° | **+0.6 〜 +1.5mm（押し込みゼロ）** |
| 1〜11、18〜19 | 3.6〜5.6° | −2.5 〜 −7.0mm |

### 残る食い違いの内訳（骨盤基準、位相 0.9〜1.0）

| | 実測 − 指令 |
|---|---|
| 遊脚の足 | **+1.6mm**（指令より高い = 追従の遅れ） |
| 支持脚の足 | **+4.1mm**（脚が指令より短い = 骨盤が沈む） |

差し引き −2.5mm で、支持足の足裏系で見た −2.6mm と一致する。
**主因は遊脚が押し下げられていることではなく、支持脚側が沈んでいること。**

## 4. 残っている問題

### 足首 ID5 が安定化の補正に追い付かない（いちばん負けている軸）

単脚支持中の |偏差|（実測 − 目標）。**支持脚の ID5 が 3.2°、最大 11.2°。**

| 役割 | 軸 | \|偏差\| 平均 | 電流 平均 / ピーク |
|---|---|---|---|
| **支持** | **ID5 足首（長ロッド側）** | **3.20°** | 0.86A / 3.21A |
| 遊脚 | ID5 足首 | 2.12° | 0.44A / 2.56A |
| 遊脚 | ID1 股ピッチ | 1.39° | 1.10A / 3.31A |
| 支持 | ID4 膝 | 0.72° | 3.76A / 11.87A |

**トルク不足ではない。** 電流は平均 0.86A で 3.0A 超えは 2.3% だけ、目標の動く速さが
`move_speed` 2000 step/s を超えるのも 1% だけ。力も速度上限も余っているのに 3° ずれている。

原因は安定化の補正の速い動き。補正の有無で比べると ID5 だけ 4 倍になる（bag `02_11_24`）。

| 支持脚の軸 | 補正あり | 補正なし |
|---|---|---|
| **ID5 足首** | **2.93°** | **0.70°** |
| ID4 膝 | 1.11° | 0.81° |
| ID2 股ロール | 0.41° | 0.47° |

足首は足裏の向きをほぼ 1:1 で決めるので、**支持足の足裏が指令より 3° ずれた向きで床に着いている**。
安定化が「足裏をこう回して立て直せ」と言っても、その 3 割前後は実行されていない。
記録は 10Hz なので、補正の速い揺れ自体は bag には写っていない（`rate_limit` 4 rad/s = 229°/s）。

### 膝 ID4 は「力で押している」側

電流は平均 3.2A、**53% の時間で 3.0A 超**、ピーク 12〜13A。それでいて偏差は 0.7°。
よく働いているが位置は保てている。保護電流の上限に張り付いているかは**未確認**。

### 関節の外のたわみ（沈み）

板も押し込み撤廃も、ここには効かない。詳細は `docs/サーボ追従と両足支持_実装計画.md` と
別途の解析（補正なしの歩でも位相 0.6 で接地、股ロールのたわみで遊脚が 15〜20mm 下がる）。

## 6. 調べ方の再現

解析スクリプトは scratchpad の使い捨てで、リポジトリには無い。同じ図を出すなら:

```bash
# 歩行区間とロールの概観（既存のツール）
python3 scripts/bag_walk_roll.py ~/roboone_logs/rosbag2_<日時>

# 足裏の位置は leg_service に流し込んで FK で出す（1 行 1 リクエスト）
printf "mech 0\nfk R <t1> <t2> <t3> <t4> <t5> <t6>\n" | ros2 run roboone_kinematics leg_service
#   角は /joint_states（実測）か /motion/joint_commands（指令）の順で deg。
#   並びは hip_pitch, hip_roll, hip_yaw, knee, ankle_pitch, ankle_roll = J1..J6
#   出てきた両脚の (foot, R) から、支持足の足裏系での遊脚の 4 隅の高さを出す

# 板が計画の全時刻で届くか（バスを開かない。方式が板のときだけ出る）
ros2 run roboone_motion motion_node --ros-args -p dry_run:=true -p allow_torque:=false \
  -p walk_mode:=static -p stab.board:=true 2>&1 | grep "板の補正"
```

サーボの負け具合は `/motion/servo_states` の `position`（実測カウント）と `velocity`（目標カウント）の差、
`/motion/servo_current` の `velocity`（区間平均）と `effort`（区間ピーク）で見る。1 count = 0.088°。

立位で関節角を 1 count 動かしたときの足先の高さの変化: 膝 0.109mm / 股ロール 0.026mm /
股ヨー −0.015mm / 股ピッチ・足首 0.000mm。

## 7. 注意

- **`walk_engine.hpp` にユーザの足踏み実験（`lx = 0`）が未コミットで残っている。**
  コミットには入れていない。動歩行の照合はその 1 行を戻した一時コピーで行う
  （手順は `docs/commands.md` の「静歩行」）。
- `static_gait.yaml` は 2026-09-18 時点で**時間を 3 倍（速さ 1/3）にした観察用**の値。
  元の値はファイル冒頭に書いてある。
- 上の実測（bag `04_00_45`）は **`com_offset_y` = −20mm のときのもの**。同日 04:09 の
  `15f7fc5` で 0 に戻っているので、取り直すと数字は動く。
- motion ノードは `static_gait.yaml` も `walk_mode` も**起動時にしか読まない**。
  設定を変えたら `colcon build --packages-select roboone_walk_ref` して launch し直す。
- 2026-09-18 の作業中、`pkill -f motion_node` で**ユーザが走らせていた motion ノードまで落とした**。
  bag `04_00_45` が 141s で終わっているのはそのため。ノードを止めるときは PID を確かめること。
