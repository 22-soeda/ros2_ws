## 1. 確定した値と、そこから決まった値

**θ4_zero = 89.3°（確定）** —— 脚が伸び切った姿勢（T ポーズ）でのロッカー角。
これが決まったことで、暫定だった σ_knee も決まった。

```
[T ポーズ] 曲げ量 0 のとき
  公開角 θ4      0.000000°
  |o3 → o5|      283.521000 mm  (伸び切り ℓ3' + ℓ4 = 283.521000 mm)
  ロッカー角     89.3000°
  クランク角 θ2  185.7067°
```

曲げ量 0 で本当に脚が伸び切っていることは、脚 IK 側の関節位置で確かめてある。
股中心 o3 から足首ロール軸 o5 までが ℓ3′ + ℓ4 ちょうど（283.521000 mm、誤差 < 1e-9）に
なるので、「曲げ量 0 = T ポーズ = ロッカー 89.3°」の 3 つが同じ姿勢を指している。

### σ_knee は選べない

```
[σ_knee の一意性]
  σ = +1: 屈曲 0〜150.0° まで到達（伝達比の最小 1.822）
  σ = -1: 屈曲 0〜60.3° まで到達（伝達比の最小 0.032）
```

σ = −1 は屈曲 60.3°（θ4 = 28.96°）で死点に当たる。そこでは**伝達比が 0.03 まで落ちて
サーボが膝を動かせなくなる**ので、設計可動域 0–150° に届くのは +1 だけ。選択の余地が
ないので暫定値ではなくなった。`test_sigma_is_unique` と C++ の `testSigmaUniqueness` が
毎回この一意性を検算する。

## 3. C++ 実装と、Python との突き合わせ

C++ 版はヘッダオンリ・ROS 非依存・ヒープ無しで、`leg_kinematics.hpp` /
`ankle_parallel.hpp` と同じ流儀。**逆変換 1 回あたり 0.157 µs**（Pi 5、20 万回平均）なので
200 Hz の制御ループから直接呼べる。

独立に書いた 2 つの実装を、同じ寸法・同じ枝・同じ θ2 で突き合わせた。実機寸法だけでなく
r₁ ≠ r₄・平行四辺形・r₁ = 0・無関係な寸法の 7 ケースを通してある。

```
  [0] r=(20, 45, 35, 20) β=-1 ε=+1 θ4_zero=89.3° σ=+1
        θ2 160〜270° を 441 点（うち両方が解けた 441 点）
        角 θ3 2.54e-14 / θ4 5.09e-14 / IK θ2 5.09e-14 deg
        伝達比 1.33e-15 / γ 7.63e-14 deg
        速度 1.33e-15 / 加速度 6.66e-15
        曲げ量 6.36e-14 / サーボ 5.09e-14 deg
        到達可否の判定が食い違った数 0
```

7 ケースすべてで角は 1e-12 rad 台以下、到達可否の判定の食い違いは 0 件。比べているのは
θ3・θ4・逆変換の θ2・伝達比・伝達角・速度・加速度・曲げ量・サーボ角の 9 つ。

## 4. 脚 IK との繋ぎこみ

呼び出し順は

```
脚IK → (θ1..θ6) → { J1–J3 は直結 / J4 は 4 節リンク / J5–J6 は足首パラレルリンク } → サーボ指令
観測は逆順
```

C++ の `leg_servo.hpp` が 3 つとも束ねていて、motion ノードは `legServoFromJoints()` /
`legJointsFromServo()` の 2 行で書ける。Python の `leg_servo.py` は膝まで（足首の Python 版は
無く、頼まれたら `AnkleNotImplemented` を送出して素通しに気づけるようにしてある）。

膝の読み替えは 2 段で、どちらも ±1 の掛け算なので往復とも同じ式でよい。

```
[1] 公開角 -> 曲げ量    θ4_S = θ4_pub · sign[knee] · (X-swap)   AXIS_FLIP と座標系
                        bend = σ_leg · (θ4_S − φ)
[2] 曲げ量 -> ロッカー   θ4_rocker = σ_knee · bend + θ4_zero
```

`[1]` は既定値だと Python 側で bend = −θ4_pub、C++ 側で bend = +θ4_B になる。
**同じ姿勢を指しているが公開角の符号が違う**（Python は文書の Σ_0、C++ は機体座標 Σ_B で、
(X-swap) が 1 段多く入る）ので、両者の θ4 の数値を直接見比べてはいけない。

往復の実測

```
[往復] θ4 -> サーボ -> θ4（屈曲 0〜150°）最大誤差 1.14e-13 deg
       必要なサーボ振り幅 74.01°（185.71° 〜 259.71°）

[脚 IK と接続] fk → ik → サーボ → 関節角 を 2000 姿勢: 膝の最大誤差 1.96e-10 deg
```

C++ 側も同じで、`ik()` が返した公開角から膝サーボを出して戻す往復を 2000 姿勢で
最大 2.32e-10 deg。可動域内で解けなかった姿勢は 0 件。

## 5. 参照値と合わなかった2点

依頼の参照表のうち2つは再現しなかった。どちらも実装ではなく**表の側の誤り**と判断している。

**組める θ2 の区間** —— 表 70.8°–289.2° に対し実装は **70.5288°–289.4712°**。
境界は閉形式で解ける。`d² = r1² + r2² + 2·r1·r2·cos θ2 = 2425 + 1800·cos θ2` に
三角不等式 `d ≤ r3 + r4 = 55` を入れると `cos θ2 ≤ 1/3`、すなわち
`θ2 ≥ arccos(1/3) = 70.5288°`。もう一方の `|d − r4| ≤ r3` は d ≤ 55 に含まれるので効かない。
表のほうが 0.27° 内側に寄っている。

**Freudenstein の K₃** —— 表 0.3389 に対し実装は **0.8889**。
K₁ = r1/r4 = 1 と K₂ = r1/r2 = 0.4444 は表と一致しているので定義は同じものを指している。
その定義で `K₃ = (r1² + r2² + r4² − r3²)/(2·r2·r4) = 1600/1800 = 0.8889`。
0.3389 は `膝4節リンク導出.pdf` の**仮置き寸法**での K₃ = 0.3838 に近く、新寸法へ
差し替えるときの写し損ねと思われる。恒等式そのものは成り立っていて、(KN-9) の残差は
作動域全体で最大 7.8e-16。

### サーボの原点だけは左右で別

**膝サーボは左右とも ID 4** で、どちらのバスに繋がっているかが左右を決める
（`/dev/feetech_left` の ID4 = 左膝、`/dev/feetech_right` の ID4 = 右膝）。
4 節リンクの幾何そのもの（r₁–r₄, β, ε, θ₄_zero, σ_knee）は左右共通だが、
**サーボの原点は取り付けごとの実測値なので左右で違う**。実際
`feetech_servo/config/servo_home.yaml` の ID4 は

| | home [count] | = [deg] |
|---|---|---|
| `/dev/feetech_left` | 2095 | 184.13 |
| `/dev/feetech_right` | 1835 | 161.28 |

で **22.85° ずれている**。したがって φ₀・σ_m・n は左右別に持つ必要があり、
`knee_config.py` は `{"right": …, "left": …}` の dict、`knee_config.hpp` は
`{RIGHT, LEFT}` の配列にしてある。取り出しは `knee_fourbar(side)` /
`makeKneeParams(Side)`。

なお、この home が「脚を伸ばし切った姿勢」で取られたものなら φ₀ はそのまま計算できて
左 −1.58°・右 −24.43°（σ_m = +1, n = 1 のとき）になる。ただし `servo_home.yaml` は
「狙いの姿勢」としか書いておらず伸び切りとは限らないので、**この値は当てにせず**
テストランで実測すること。

## 7. 設計上の申し送り

伝達比は膝の曲げ量 0–120° の区間で **1.870–2.217**。モータ 1° が膝 2° 前後を動かす増速で、
そのぶんトルクは約半分になる。膝は歩行中いちばんトルクを要求する関節なので、サーボ選定と
飽和判定でこの2倍を効かせること。区間内で 19% 変わるので、姿勢によらず一定と置かない。

伝達角は 44.93°–89.73° で、設計の目安 40°–140° に収まっている。屈曲 150° まで使っても
109.99° で目安の内側。

## 8. 実機での動作確認（テストラン）

膝を手で曲げて、そのモータ回転から 3D モデルの膝と 4 節リンクがリアルタイムに追従する
ことを見るための一式。**トルクは入れず、角度だけを読む。**

### 構成

```
feetech_knee_stream (C++)     サーボの角度を読むだけ。JSON を 1 行 1 サンプル流す
        ↓ stdout
serve_knee3d.py               生角 → クランク角 θ2 → 順変換 (KN-5) → ロッカー角 θ4
                              → 曲げ量 → 脚の関節位置。HTTP で配信
        ↓ /api/state
knee3d.html                   3D 表示（脚 + 4 節リンク）と矢状面の拡大図
```

### 安全側の作り

ストリーマは**サーボに書き込む経路を持たない**。唯一の例外は起動時のトルク OFF（脱力）
1 回だけで、手で膝を動かせるようにするためのもの。位置指令も EEPROM も触らず、
`init_motor()` も呼ばない（あれは既定でトルクを入れるため）。`--keep-torque` を付ければ
そのトルク OFF すら行わない。

### 伸び切りの基準は「記録された初期位置」

**過去に各サーボへ対応づけた初期位置を、伸び切り（曲げ量 0）のサーボ値として扱う。**
出どころは `feetech_servo/config/servo_home.yaml` の ID4 で、`feetech_calibrate_home` が
書いたファイル。起動時の姿勢は基準にしないので、脚が曲がったまま起動しても基準はずれない。

| バス | home | = |
|---|---|---|
| `/dev/feetech_left` | 2095 | 184.13° |
| `/dev/feetech_right` | 1835 | 161.28° |

φ0 は σ_m と n に依る派生量なので定数では持たず、`phi0_from_home()` が
φ0 = φ(home) − σ_m·n·θ2_ext で作る（σ_m = +1, n = 1 なら 左 −1.576°／右 −24.427°）。
`knee_config` にも `SERVO_HOME_COUNT` を置いてあり、サーバは yaml を直接読んで
両者が食い違ったら警告を出す（原点を取り直したら `knee_config` も写し直す）。

画面には「基準の生カウント／出どころ／今との差」が出る。**脚を伸ばした状態で曲げ量が
0 付近にならなければ home の取り直しを疑う。** 今の姿勢を一時的に基準にしたいときだけ
「今を伸び切りに（一時）」を押す（yaml は書き換えない）。

### 途中で踏んだ SDK のバグ（修正済み）

50 Hz で回すと `feetech_knee_stream` が数百 ms で異常終了した
（`double free or corruption (out)` = SIGABRT）。AddressSanitizer で追うと、
ベンダ SDK の `vendor/scservo/src/SCSerial.cpp` の受信ループ

```c
rvLen += read(fd, nDat + rvLen, nLen - rvLen);   // ← 戻り値を検査していない
```

が原因だった。`read()` がエラーで **−1** を返すと `rvLen` が −1 になり、次の周回が
`read(fd, nDat - 1, nLen + 1)` となって**バッファの 1 バイト手前へ書き込む**。
ASan の指摘は「21 バイト領域の 1 バイト手前に 17 バイト WRITE」。

戻り値を検査してから加算するよう直した（短い受信は上位が「欠損」として扱うので、
そこまでの受信長を返せばよい）。修正後は 8 秒 400 サンプルで ASan エラー 0・正常終了。

**この受信ループは全ツール共通の経路**なので、`feetech_demo_node` や `feetech_shell`、
歩行時の状態読み取りも同じバグを踏みうる。踏むのは read() がエラーを返すとき、
つまり**受信が間欠的に欠ける低電圧・高レート時**で、これまで「たまに落ちる」形で
出ていた可能性がある。

### 表示上の断り

4 節リンクを脚のどこに描くかについて、**リンクの取り付け向き**（O₄→O₂ が大腿のどちらを
向くか）は寸法 r₁–r₄ からは決まらないので、表示では大腿の中心線上（膝から股方向に
r₁ = 20 mm）に置いている。**動き方は取り付け向きに依らず正しい** —— 地節は大腿に、
ロッカーは下腿に固定されているので、機構全体は大腿・下腿と一体で回るため。上の
「ロッカーと下腿が一体で回ること」がそれを数値で確かめている。
