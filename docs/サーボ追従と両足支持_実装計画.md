## 1. 分かったこと

### 1.1 計画は前後に動いていなかった

- `/motion/stab` の `ff_ax`（計画上の重心の前後加速度）は、3 回の歩行で常に 0。
- `/motion/joint_commands` を FK に通した足先の前後位置は 0〜2 mm。
  両足の前後差は平均 +0.4 mm。
- ビルド（23:59:11〜00:00:02）は編集（23:58:59）より後、launch（00:00:22）はビルドより後。
  変更後のバイナリで走っている。

### 1.2 実測の足先は毎歩 約 10 mm 前に着地していた

`/joint_states`（サーボのエンコーダ値）を FK に通した値。

| | 指令 | 実測 |
|---|---|---|
| 両足接地の瞬間の前後差（着地した足 − 離れる足） | +0.4 mm | **+10.2 mm**（−0.6〜+17.1、57 歩中 56 歩で正） |
| 遊脚の前後位置 | 0 | 上昇中 −15 mm → 下降中・着地 +4〜5 mm |
| 支持足の前後位置 | 0 | 着地直後 +3〜5 → 中盤 −4（高さは指令より 5 mm 上） → 離地直前 −7〜−8 mm |

1 歩 10 mm × 1.67 歩/s ≈ 17 mm/s。滑りがなければ 20 秒で約 35 cm 進む。

### 1.3 関節ごとの遅れ

`/motion/servo_states`（position = 実測カウント、velocity = 目標カウント）で、
「実測(t) と 目標(t − τ) の差が最小になる τ」を出したもの。値は左右でほぼ同じ。

| 軸 | P ゲイン | 遅れ（支持中 / 遊脚中） | 目標の速さ（10 Hz 平均の最大） | 負荷の最大 |
|---|---|---|---|---|
| 股ピッチ ID1 | 32 | 65〜70 / 80 ms | 約 1040 step/s | 24 % |
| 股ロール ID2 | 32 | 90〜95 / 110〜115 ms | 約 980 | 39 % |
| 股ヨー ID3 | 32 | 85〜90 / 90 ms | 約 545 | 23 % |
| 膝 ID4 | **128** | **35〜40 / 50 ms** | 約 980 | 51 % |
| 足首・短い腕 ID6 | 32 | 90 / 85〜90 ms | **2500〜2860** | **93〜100 %** |
| 足首・長い腕 ID5 | 32 | **145〜150 / 125〜135 ms** | **4180〜4230** | 72〜82 % |

- 9/16〜9/17 の歩行 bag でも同じ傾向（股ピッチ 70〜85、股ロール 85〜115、
  ID5 120〜145 ms。足首の要求はすべての回で 2000 step/s を超える）。
- 電源と通信は正常だった（バス電圧 11.3〜11.9 V、全軸応答、エラービット 0。
  電流の最大は 13 A）。
- 記録の周期が 10 Hz なので、遅れの推定は ±5〜10 ms 程度の粗さがある。

**前進した仕組み:** 足を 50 mm 上げる動きは、股ピッチと膝の組み合わせで作っている。
膝だけが股ピッチより約 30 ms 先に動くので、上げるときは膝が先に曲がって足先が後ろへ、
下ろすときは膝が先に伸びて足先が前へ振れ、前に出たまま着地する。
**全関節が同じだけ遅れるなら、足先の軌道は形を保ったまま時間がずれるだけで、
前後のずれは生まれない。** 問題は遅れの大きさより、遅れの差にある。

### 1.4 遅れの原因

1. **位置制御が P だけ（P=32 / D=32 / I=0）。** 動く目標に追従するには、
   速さに比例したずれが常に要るので、一定時間の遅れとして現れる。長さはほぼ P に反比例する。
   - 膝（P=128、2026-08-28 に変更）が P=32 の軸より 30〜35 ms 速い。
   - 支持中と遊脚中で遅れがほとんど変わらない。荷重やトルク不足が原因ではない。
   - 「遅れ = 共通部分 + P に比例する部分」とおいた 2 点からの粗い見積もり:
     共通部分 約 35 ms、P に比例する部分 約 45 ms（P=32）/ 約 11 ms（P=128）。
2. **どの軸にも乗る約 35 ms の中身。**
   - 記録上の見かけの遅れ 10〜15 ms。実測は 50 Hz でしか読まない（平均 10 ms 古い）うえ、
     書き込みスレッドが指令を拾うまでに最大 5 ms かかる。実機の動きには関係しない。
   - サーボ内部の加減速（**仮説**）。`move_acc` 254 は約 39 rad/s²。目標ごとに
     「そこで止まるつもり」で減速しているなら、速さ v で v/(2a) 遅れる
     （1000 step/s で約 20 ms）。HLS のファームウェアがそう動くかは未確認。
3. **足首は速度と力が足りない。**
   - `move_speed` 2000 step/s は、規格書（`feetech_servo/docs/HLS3950M_規格書.pdf`）の
     無負荷最高速度 0.133 s/60°（≈ 5100 step/s、12 V）の 39 %。足首の要求はこれを超える。
   - 規格書の特性図では、出せる速度は負荷に比例して落ち、50 kg·cm で 0 になる。
     電圧も定格 12 V を下回っている。型番 4618 / 5130 のどちらがこの規格書に当たるかは未確認。
   - ID5・ID6 は型番 5130 で、保護電流が 3.25 A（4618 の半分）。
   - 遅れを補正しても 3〜9° の誤差が残る。単純な時間遅れではなく飽和している。
4. **要求される動き自体が速い**（§1.5）。

### 1.5 要求速度の出どころ

歩行計画の Python 原本（`walk_core`）で足踏み（`lx = 0`、`/cmd_walk` 0.06 m/s）を回し、
C++ の機構層 `leg_service` でサーボ角に直して、200 Hz の差分から出した値（右脚）。
25 ms の中央値で均し、着地の 1 周期のとび（§1.7）は除いてある。単位は step/s。

| | ID1 股ピッチ | ID2 股ロール | ID3 股ヨー | ID4 膝 | ID6 足首・短 | ID5 足首・長 |
|---|---|---|---|---|---|---|
| 現状（T 0.60 / W 170, −15 / 足上げ 50 mm） | 1223 | 1083 | 608 | 1153 | **2626** | 1792 |
| 足上げだけ（骨盤の横振りを止める） | 1271 | 1 | 135 | 1228 | 1318 | 1592 |
| 横振りだけ（足上げ 0） | 218 | 1082 | 608 | 257 | 1833 | 1792 |

- 股ピッチ・膝は足上げだけ、股ロール・ヨーは横振りだけで決まる。ID6 は両方が重なる。
- **横振り:** 支持足が入れ替わる瞬間、骨盤は 0.50 m/s で横切り、横の重心加速度は
  −3.2 → +3.9 m/s² に跳ぶ（bag の `ff_ay`）。ZMP を歩の間ずっと支持足に置く計画では、
  この速さはほぼ (W/2)·ω（ω = √(g/z_c) = 6.13 /s）で決まり、**周期 T を延ばしても下がらない**
  （T → ∞ で 0.52 m/s）。
- **足上げ:** 50 mm を周期の 45 % の時間で上げるので、足上げの高さに比例し、周期に反比例する。
- 足首ロールの振れ 33° に対して、パラレルリンクのサーボは 60〜78° 動く。
- 9/17 に横振りを増やした（`foot_spacing` 170）ことで、股ロールの振れは 21.6° → 26° に増えている。

### 1.6 安定化の補正が足首の要求を押し上げている

- 実機の ID5 の要求は、10 Hz 平均で 4179 step/s。計画から出る値（同じく 10 Hz 平均）は
  1411 で、**約 3 倍**。ID6 は 2859 対 2341。
- 補正（足首ピッチ）の変化の速さは最大 233 °/s で、`stab.rate_limit` の 4 rad/s（229 °/s）に
  張り付いている。補正の大きさは ±6.9° で、`ankle_clamp`（0.12 rad）に当たっている。
- 歩行中の 31 % の周期で「安定化の補正を入れると解けないので、補正を外して出した」が
  起きている（その周期だけ補正が一瞬消える）。

### 1.7 着地の瞬間の段差

遊脚は床より `td_overdrive`（4 mm）下まで押し込まれ、歩の境界で 1 周期（5 ms）のうちに
0 へ戻る。この瞬間だけ、要求速度は ID1 3562 / ID4 3268 / ID5 5913 step/s に跳ぶ。
距離は小さいが、余計な衝撃になる。

## 2. 実装計画

### 段階 1: 測る道具をリポジトリに置く（実機の経路の外）

- `scripts/bag_servo_lag.py`: bag から、軸ごとの遅れ・要求速度・負荷を、支持中と遊脚中に分けて出す（§4.1）。
- `scripts/servo_demand.py`: 歩行計画と `leg_service` から、パラメータごとの要求速度を出す。
  足踏み（前後の歩幅 0）も指定できるようにする（§4.2）。
- `docs/commands.md` に使い方を追記する。

以降の変更は、すべてこの 2 つの数字で良し悪しを判断する。

### 段階 2: パラメータだけで足首の要求を下げる（コードは変えない）

- `stab.rate_limit` を 4 → 1〜2 rad/s にする。実行中に変えられる:
  `ros2 param set /motion stab.rate_limit 1.0`
- `gait.yaml` の `swing_height` を 0.05 → 0.03 にする。20 mm で床を擦った実績（2026-08-29）が
  あるので、30 mm で擦らないかを実機で確かめる。

どちらもトルクを入れた実機での確認になる（実行のたびに確認を取る）。

### 段階 3（本命）: 両足支持の間に ZMP を移す

`walk_core` に `ds_time`（両足支持の時間 Td）を足す。**既定 0 で今と完全に同じ動き**にする。

#### 1 歩の構成

| 区間 | 長さ | ZMP | 足 |
|---|---|---|---|
| 両足支持 | Td = `ds_time` | 前の支持足 p_{i−1} から新しい支持足 p_i へ直線で移す | 両足とも接地 |
| 片足支持 | Ts = `t_step`（今のまま） | p_i に固定 | 遊脚はこの間だけ動く（足上げの速さは今と同じ） |

#### 計算を変える 3 か所

1. **DCM の進め方（`advance_dcm`）。** 両足支持中は ZMP が p(t) = p₀ + ṗ t で動くので、
   ```
   ξ(t) = p(t) + ṗ/ω + (ξ₀ − p₀ − ṗ/ω)·e^{ωt}
   ```
   片足支持中は今の式のまま。
2. **定常状態での DCM のずれ（`step_params`）。** 1 歩で
   ```
   ξ_end − p_i = e^{ωT}·(ξ₀ − p_{i−1}) − e^{ωTs}·κ·(p_i − p_{i−1})
   T = Td + Ts,  κ = (e^{ωTd} − 1) / (ωTd)
   ```
   2 歩周期の定常解は（l₁ = 今回の足の変位、l₂ = 次の変位、E = e^{ωT}）
   ```
   ξ₀ − p_{i−1} = e^{ωTs}·κ·(E·l₁ + l₂) / (E² − 1)
   ```
   Td → 0 で今の b の式に戻る。LIPM の数値解と 0.001 mm まで一致することを確認済み
   （Ts 0.6 / Td 0.4 / ZMP ±70 mm で ξ₀ = −17.939 mm、Td 0.8 で −41.672 mm）。
3. **着地点（`update_landing`）。** 予測した歩の終わりの DCM から、上の式を今回の変位 l₁ に
   ついて解く。

#### その他の扱い

- 歩き出しの押し出し（START）は、最初の両足支持として扱う（両足の中点 → 最初の支持足）。
- 停止は、最後の両足支持で ZMP を両足の中点へ移す。
- 両足支持中の出力は support = 0（両足）。安定化はすでに「両足支持なら両脚へ補正」の扱いを
  持っているので、そのまま使える。位相（phase）は片足支持の区間で測る。
- 遊脚の到達判定（`checkSwingLanding`）は Ts で行う。

## 3. 決めること・リスク

1. **歩くのが遅くなる。** 歩幅 = v × 1 歩の時間なので、1 歩を 1.0 s にすると、今の
   `v_max` のままでは歩幅が 1.7 倍になり足が届かない。`v_max` を 0.10 → 0.06 m/s 程度に
   下げることになる（最高速 4 割減）。歩幅を v × Ts にする選択肢もある。
2. **計画のずれに弱くなる（一番のリスク）。**
   - 1 歩の間に誤差が増える倍率 e^{ωT} が 40 → 460（Td 0.4）/ 5340（Td 0.8）になる。
   - 着地点でずれを吸収するのに要るずらし量が e^{ωTd}/κ 倍（Td 0.4 で 2.7 倍、0.8 で 4.9 倍）になる。
   - 指令の変化の速さの上限 `a_max` の許容値は、T² に反比例して狭まる見込み
     （T 1.0 で (0.11, 0.05) → (0.04, 0.018) m/s² 程度）。今の (0.06, 0.03) はこれを超える。
     **導出はやり直しが要る**（`params.py` の不等式に相当するもの）。
   - 両足支持中は ZMP を支持多角形の中で自由に置けるので、そこで DCM を補正する手もある。
     ただし純フィードフォワードの枠を出る。
3. **「計画だけ足間隔を広く取る」工夫（`foot_spacing` 170 / `stance_y_offset` −15）は
   要らなくなるかもしれない。** ZMP を実際の足の位置（±70 mm）で移しても、骨盤は支持足まで
   7 mm に寄った。両足支持を使うときの値は決め直す。
4. **静歩行モード（別の作業）と作業範囲が重なる。** 静歩行の次の段階（C++ 版、motion への
   組み込み、安定化の支持脚の判定の拡張）と、`walk_engine.hpp` の周辺・安定化・照合ツール・
   `walkcore.js` がぶつかる。静歩行の組み込みが終わってから入るか、先に分担を決める。
5. **足踏み実験（`lx = 0`）の扱い。** `step_params()` を書き換えるので、実装中もその行は残し、
   コミットからは外す。「足踏みモード」として正式なパラメータ（既定は無効）にする手もある。
6. **P ゲインの見直し（別案）。** 股 3 軸と足首の P を膝に揃えて上げる
   （`feetech_gains --scale-p 2 --write`。EEPROM への書き込み）と、遅れの差そのものが
   縮まる。段階 3 とは独立に試せる。関節ごとに指令を遅れの分だけ先出しする案もある
   （ソフトだけで済むが、速度が頭打ちの足首には効かない）。

## 4. 数字の取り直し方

2026-09-18 の解析に使ったスクリプトは一時フォルダに置いたもので、リポジトリには無い。
段階 1 で正式に置くまでは、以下の手順で再現する。

### 4.1 bag から遅れと足先の位置を出す

- `/motion/servo_states` の position（実測カウント）と velocity（**目標カウント**）で、
  歩行区間（`/motion/state` が WALK）について、実測(t) と 目標(t − τ) の二乗誤差が最小に
  なる τ を 5 ms 刻みで探す。支持中・遊脚中は `/motion/stab` の `support` で分ける。
- 足先の位置は `/joint_states` と `/motion/joint_commands` を `scripts/leg_ik.py` の `fk()` に
  通す。**左脚は `leg_params('left', flip=(1, 0, 0, 0, 0, 0))` を渡すこと。**
  `scripts/leg_config.py` の `AXIS_FLIP_LEFT` は `None` だが、C++（`leg_config.hpp`）は
  左の股ピッチを反転している（`{1, 0, 0, 0, 0, 0}`）。この食い違いは未修正。
- 計画に前後の動きがあるかは、`/motion/stab` の `ff_ax` で見る。

### 4.2 要求速度を計算する

- `roboone_walk_ref.walk_core.engine.WalkEngine` を継承し、`_step_params()` の中だけ
  前後の速度を 0 にすると足踏みになる。200 Hz で回し、`foot_targets_pelvis()` に
  `stance_y_offset` を足して Σ_B [mm] にする（足裏の向きはホーム姿勢と同じ 0）。
- `install/roboone_kinematics/lib/roboone_kinematics/leg_service` に、`mech 1` のあと
  `ikpose <R|L> x y z 0 0 0` を 1 行ずつ流す。応答の `mech.dservo`（T ポーズ基準のサーボ角 [deg]、
  ID 順 1,2,3,4,6,5）を差分して step/s（× 4096/360）にする。着地のとび（§1.7）を除くため、
  25 ms の中央値で均す。
- 両足支持で ZMP を移す場合は、横方向の LIPM を ZMP の区分関数で積分し、
  反周期条件 x(T) = −x(0) を線形方程式で解いて周期解を得る。
