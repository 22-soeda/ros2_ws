# roboone_perception

敵機検出。**D435if の depth と IMU から `/opponent` と `/ring_edge` を出す**
`opponent_detector` ノードと、その計算部分（ROS 非依存）。

アルゴリズムの仕様は `docs/opponent_detection.pdf`（技術ノート(4)）、
出す先の約束は `docs/behavior_planning.pdf`（技術ノート(3)）§5.1、
ノード構成は `docs/ros-architecture.md`。本 README には**そこから変えたところと、
その理由**を書く（`docs/ros-architecture.md` は別リポジトリの複製なので直接は編集しない）。

## 起動

```bash
# カメラごと（ロボット無しで検出だけ確認できる形）
ros2 launch roboone_perception opponent_detector.launch.py camera:=true

# カメラが既に上がっているなら検出器だけ
ros2 launch roboone_perception opponent_detector.launch.py

# 機体まるごとの中で
ros2 launch roboone_bringup roboone.launch.py camera:=true detector:=true
```

テストラン（ブラウザのリアルタイムビューア。検出器 + 転倒判定。サーボには触れない）:

```bash
ros2 launch roboone_perception opponent_testrun.launch.py camera:=true
ros2 run roboone_perception opponent_viewer --demo      # 実機なし。合成シーン

# ★トルクが入る。ホーム姿勢へゆっくり（既定 6 s）立たせてから見る。機体を支えること
ros2 launch roboone_perception opponent_testrun.launch.py camera:=true home:=true
```

`home:=true` は既定 false。false のときは motion ノードを上げず、`/estop` にも
`/cmd_motion` にも publisher を作らない。止めるのは画面の「脱力」か Ctrl-C。

**`bag:=true`** を足すと、見ているものをそのまま bag に録る（`~/roboone_logs/opp_<日時>`）。
実機なしで同じ入力を流し直せるようになる。depth は 24.4 MB/s あって SD カード
（実測 22.5 MB/s）に入らないので、**カメラと検出器は 30 Hz のまま**、bag に入れる分だけ
`depth_throttle` が 10 Hz に間引く（`bag_hz:=` で変えられる）。

何をどう判定しているかと、確かめる順は `docs/相手機の認識.md`。

確認:

```bash
ros2 topic echo /opponent
ros2 topic echo /ring_edge --once
ros2 run rqt_image_view rqt_image_view /detector/debug   # 図7 と同じ俯瞰図
ros2 run roboone_perception detector_bench --duration 30 # 周期と段ごとの時間
ros2 run roboone_perception height_probe                # 床が実際どこにあるか (下)
```

**realsense-viewer で録った `.bag`**（ROS1 形式。練習会の `bag_0712/` など）は
`opponent_bag_viewer` で同じ検出器に流して見る（既定 8106 番）。bag ごとにカメラの
取り付け（鉛直・高さ）を IMU と床の平面から測ってから流し、深度画像に塊を画素ごとに
重ねた図と側面図が増える。使い方と注意は `docs/commands.md`、仕組みは `bag_viewer.py` の冒頭。

```bash
ros2 run roboone_perception opponent_bag_viewer bag_0712/
ros2 run roboone_perception opponent_bag_viewer bag_0712/ --batch   # 画面なしの要約
```

**「リング面が取れない」から抜けられないとき**は `height_probe`。検出器の状態を
使わずに、IMU の加速度を鉛直として depth の高さヒストグラムをそのまま出す。
`body.cam_height` がずれているのか、検出器の鉛直が漂っているのかが分かれる
（実機を立たせたまま並行して走らせてよい。読むだけで何も書かない）。

## トピック

| トピック | 型 | 向き | 周期 |
|---|---|---|---|
| `/camera/depth/image_rect_raw` | sensor_msgs/Image (16UC1) | 受ける | 30Hz |
| `/camera/depth/camera_info` | sensor_msgs/CameraInfo | 受ける | 30Hz |
| `/camera/imu` | sensor_msgs/Imu | 受ける | 200Hz |
| `/detector/reset_attitude` | std_msgs/Empty | 受ける | 基準姿勢の取り直し（下） |
| `/autonomy` | std_msgs/Bool (latched) | 受ける | true への立ち上がりで基準姿勢を取り直す |
| `/opponent` | roboone_interfaces/Opponent | 出す | depth と同じ |
| `/ring_edge` | std_msgs/Float32MultiArray | 出す | depth と同じ |
| `/detector/debug` | sensor_msgs/Image (rgb8) | 出す | 購読者がいるときだけ |

`/ring_edge` の並びは方位ビンで、ビン `k` の中心方位は

```
θ_k = -half_fov + (k + 0.5) · 2·half_fov / bins    [rad]
```

（既定 `bins=64`, `half_fov=45°`。`layout.dim[0].label` にも入れてある）。
**見えていない方位は NaN。**「縁が無い」ではなく「見ていない」を意味する。

## ros-architecture から変えた 4 点

### 1. 入力を点群ではなく深度画像にした

アーキ文書の表では `opponent_detector` は `/camera/…/points` を購読することに
なっているが、点群では検出パイプラインが成立しない。

- §4 の間引きは「d **画素**ごと」であって「d 点ごと」ではない。`realsense_bringup` は
  `ordered_pc=false`（無効画素を落とした 1 行 N 点）で出しているので、点群からは
  画素の並びが復元できない。
- §7 の「視野の縁とリングの端を区別する」判定には、その点がどの画素から来たかが要る。
  点群にはその情報が無い。
- 点群を作る仕事（`realsense2_camera` 側）と読む仕事が丸ごと無駄になる。

→ 検出器を上げるとき、点群は不要（`enable_pointcloud:=false`）。rviz で見たいときだけ ON。

### 2. 姿勢を `imu_filter_madgwick` からもらわない

§11 のとおり、歩行の安定化が使う姿勢（200Hz・機体の傾き）と検出が要る姿勢
（30Hz・リング面に対する鉛直）は別物で、1 本にまとめるとどちらの時定数も中途半端になる。
このノードは `/camera/imu` の生値を自分で積分し、リング面の法線で毎フレーム引き戻す。
`/imu/data` は購読しない。

### 3. `/opponent` を `PointStamped` から `Opponent` に昇格させた

技術ノート(3) §5.1 の予定どおり。転倒判定に上端高さが要る。あわせて

- `velocity` — α-β 追尾が既に持っている量（§2.1 の追加提案）。行動層で位置を微分し直すより
  遅れも雑音も小さい
- `status` — §9.2 の縮退の区別（下記）
- `kind` — クラスタ上端の絶対値で割った種別（2026-09-23。下記「高さの分類を絶対値にする」）。
  行動層はこれで転倒を判断し、高さのしきい値を持たない

を載せた。

### 4. 「見えない」を 1 つに潰さない

| status | 意味 | 行動層の扱い |
|---|---|---|
| `STATUS_OK` | 正常で相手が見えている | 通常 |
| `STATUS_NO_OPPONENT` | 正常だが視野に相手がいない | 通常の探索 |
| `STATUS_ATTITUDE_STALE` | 面あてはめの門を通らず、姿勢がジャイロ任せで劣化中 | 知覚が壊れている前提（旋回を落とす等） |
| `STATUS_RING_LOST` | リング面自体が取れない。転倒直後・場外を向いている | 同上 |

## 文書の手順から変えた 3 点（実装して分かったこと）

### リング成分の「種」を自機直下から正面手前に移した

§7 は「自機の真下 (u,v)=(0,0) のセルを含む成分をリングとする」とあるが、
**俯角 30°・高さ 0.35 m では水平 0.188 m より近い面は写らない**（§7 が自ら書いている
足元 19 cm の死角）。直下のセルは常に空なので、この規則をそのまま書くと必ず
「最大成分に落ちる」経路に入り、§7 が避けたかった取り違えがそのまま起きる。

代わりに**正面の、写り始めるあたり**（既定 u ∈ [0.15, 0.70] m, |v| ≤ 0.25 m）を種にする。
自機はリングの上に立っていて、そこからこの窓までリングは切れずに続くので、
「自分が乗っている成分を選ぶ」という根拠は変わらない。

### 方位の基準を光軸から機体前方に変えた

§2.2 は e1 を**光軸**の水平成分に取っているが、俯角 θ で下を向いたカメラは、機体が
ロールすると光軸自体が水平面内で振れる。ロール φ に対し方位が `atan(sinθ·sinφ/cosθ)`
≒ `tanθ·φ` ずれ、**俯角 30° ならロール 8° で方位が 4.6° 動く**（合成シーンで横 78 mm）。
歩行中このくらいのロールは常時あるので、行動層はありもしない方位変化を追いかける。

e1 は機体前方軸（カメラ座標で `(0, -sinθ, cosθ)` の定ベクトル）の水平成分から作る。
純ロールでは機体前方は水平のままなので振れない。`test_roll_does_not_swing_the_bearing`。

### `d_cliff` の代表を「最も近い境界セル」から「最も遠いリングセル」に変えた

上と同じ死角の話で、リング成分の内側の縁（＝死角との境目）は常に境界セルになる。
最も近い境界を代表に採ると、どの方位でも先に死角の縁が当たり、その先の本物の切れ目が
出てこない（前端 0.5 m のシーンで正面のビンがほぼ全部 NaN になった）。

外向きに最も遠いセルを採れば死角の縁は自然に無視される。加えて 2 つ足した:

- セルが張る方位幅で複数ビンを埋める。ビン幅 1.4° は 0.5 m 先のセルが張る 4° より細く、
  セル中心だけでビンに入れると間が空いて遠近が混ざる
- **遮蔽の影を崖と読まない。** 相手が縁まで影を落とす方位では床がそこで切れて見えるが
  崖ではない（1.0 m の前端が 0.55 m の「崖」として出た）。影の手前には必ず面より上の
  塊があるので、代表セルが面より上のセルに隣接していたら NaN にする

## 基準姿勢の取り直し（2026-09-20）

鉛直 u の引き戻しには 12° の門があるので、**u が一度それより外れると正しい床の法線まで
弾き続けて自力で戻れない。** 脱力した姿勢で起動して立ち上がる間や、転倒のあとに起きる
（実機のテストランで発生）。ホーム姿勢で静止しているときに `/detector/reset_attitude`
を送ると、直近 0.4 秒の加速度の平均から u を置き直す。静止していなければ置き直さず、
最大 `reset_timeout` 秒待つ。試合では `/autonomy` が true になった瞬間にも自動で走る
（`reset_on_autonomy`）。`docs/相手機の認識.md` の「基準姿勢の取り直し」。

## 水平付けのカメラと、人の棄却（2026-09-20）

カメラを胴体に**水平付け**で使うと決めたのに合わせて 4 つ足した。詳しくは
`docs/相手機の認識.md` §3・§6。

- **種の窓を自動で置く**（`tune.seed_auto`）。水平・高さ 0.365 m だと床は 0.66 m より先にしか
  写らず、固定の 0.15〜0.70 m の窓は常に空になる。
- **リングの内側 = 見えたリング面と自機の位置の凸包**（`tune.ring_hull`）。以前は「見えた
  リング面の 1 セル隣まで」しか候補にしなかったので、床が写らない近距離の相手が丸ごと
  落ちていた。リングは凸で自機はその上に立っているので、凸包は場外へはみ出さない。
- **相手の影で分断された床をつなぐ**（`tune.shadow_bridge`）。近い相手は見える床を左右に
  分け、種の窓も隠す。足すのは純粋な床の成分だけ（物の垂直な面が床の帯に落とす数セルを
  足すと、凸包が場外の人まで伸びる）。
- **外から差し込む塊を相手にしない**（`tune.intrude_*`）。レフリーの腕は高さと幅の
  フィルタを通る。リングの縁の外の「確かに外」の物とつながる塊を捨てる。
  「確かに外」は自機から見た視線で決める（`detect/polar.py`）。視野の端や間合いの中の
  相手を外の物と取り違えないため。

あわせて `match.obj_width_max` を規則の表 2 から 0.80 m にし、塊ごとの最大・最小を
`ufunc.at` から `reduceat` に替えた（候補の点が増えて cluster 段が 11.6 → 3.1 ms）。

## 高さの分類を絶対値にする（2026-09-23）

塊を**クラスタ上端 z_top の絶対値**だけで 4 つに割り、種別を `/opponent` の `kind` に
載せるようにした。境界は `match.obj_top_min` / `fallen_top_max` / `robot_top_max` の
3 つで、`detect/clusters.py` の `classify()` がこれだけを見る。

| z_top | 種別 | 扱い |
|---|---|---|
| `< 0.10` | ノイズ | 床のゴミ・ケーブル |
| `< 0.25` | `ROBOT_FALLEN` | 相手として追い、行動層が RETREAT へ |
| `< 0.60` | `ROBOT_STANDING` | 攻撃の対象 |
| 以上 | `HUMAN` | 人・腕・什器。相手にしない |

変えた理由は 2 つある。

**転倒の判定が行動層の比だった。** 「はじめ」の直後 2 秒で相手の立位高さ H_o を測り、
その 0.5 倍・0.75 倍で転倒と復帰を決めていた。比は較正が当たっているかどうかで意味が
変わるので、**会場で yaml を見ても何が起きるか読めない**。実機のテストランでは実際に
「最初の 2 秒に壁で較正して H_o = 0.69 m」が出ている（`docs/相手機の認識_実機テスト
ランの課題.md` 観測 1）。較正が外れたときの保険として「平たい」という別系統の証拠も
要っていた。絶対値にしてどちらも無くなり、行動層に残るのは時間の門だけになった。

**上端が飽和していて人と機体を高さで分けられなかった。** 点を集める帯 `tune.obj_h_hi`
が 0.90 m だったので、身長 1.7 m の人も 0.95 m の什器もクラスタ上端は等しく 0.90 m に
なる。帯を 1.20 m へ上げて z_top を実測値にした。水平付け・カメラ高さ 0.365 m では
距離 ρ で見える上端が `0.365 + 0.554 ρ` m なので、1.51 m までの人は 0.6〜1.2 m に入り、
それ以遠は帯の上限で飽和する。どちらでも `robot_top_max` を超えるので「人」に落ちる。

## クラスタリングを 3 次元にした（2026-09-23）

塊の結合を、真上から見たセルの 4 近傍連結から、**高さも入れたボクセルの 26 近傍**に
変えた（`grid.label_voxels`）。ボクセルは水平 `tune.cell` × 高さ `tune.cell_z` で、
**水平は計算量、高さはノイズの分離**で別々に決める（50 × 50 × 25 mm）。リンクの効く
距離はボクセル 1 つぶんで、真の距離クラスタリングの近似。深度の点の間隔は距離 3 m・stride=2 でも 15 mm なので、面が
ばらばらに割れる側の余裕はまだある。

**理由: ノイズ 1 点で上端が跳ねる。** 2 次元の連結では塊は「柱の集合」で、z_top は
その柱全部の max になる。相手の真上に浮いた点が 1 つあるだけで上端がそこまで上がり、
立っている相手が `robot_top_max` を超えて「人・什器」に化ける。高さで切れば浮いた点は
別の塊になり、セル数（`min_cells`）と距離依存の点数（`min_points_n0`）の門で落ちる。

**「上に物が乗っているものは相手にしない」は、明示の門として残した。** 2 次元のころは
腕と機体が 1 つの塊になる副作用でそうなっていたが、3 次元では別の塊に分かれるので、
放っておくと腕の下の機体へ踏み込む指令が出る。塊の足もとのセルのうち、**真上に別の塊が
乗っているセル**を数え、`tune.overhead_min_cells`（既定 4、0 で無効）以上なら相手に
しない。ノイズの 1〜2 ボクセルでは立たず、腕や板なら立つ。これがノイズと実体の
切り分けになる。

`/opponent` はその間 `NO_OPPONENT` になる。行動層はこれを「視野に相手がいない」として
通常の探索に入るので止まりはしない（§9.2 の縮退の区別）。腕が抜ければ次のフレームで戻る。

**実測（合成シーン・Pi 5、2026-09-23）。** cluster 段 3.44 → 4.89 ms、全体 15.3 →
16.9 ms（同じシーンで `tune.cell_z` を大きくして 1 層に潰したものとの比較）。
30 Hz の予算 33 ms には収まっている。

## 中身

```
detect/            ROS 非依存。walk_core と同じで、入力列から決定的に動く
  params.py        定数。機体 / 競技 / 実装 の 3 群（§11）。分けてあるのは §8.3 対策
  geometry.py      逆投影とリング平面座標（§4, §2.2）
  attitude.py      鉛直 u。ジャイロで運び、面法線で引き戻す（§5）
  ring.py          高さヒストグラムで h_r、近距離の面あてはめ（§6, §5.4）
  grid.py          占有グリッド・モルフォロジ・連結成分（§7）。ボクセルの 26 近傍も
  edge.py          d_cliff(θ)（§7）
  polar.py         自機から見た方位ごとの索引。影と「確かにリングの外」
  clusters.py      リング内の塊（3 次元）と選択（§8）
  tracker.py       α-β 追尾（§9.1）
  pipeline.py      段の並び。姿勢と知覚の閉ループはここ（§3）
sim/scene.py       合成シーン（単体テストとビューアの --demo が使う）
opponent_detector_node.py   トピックとパラメータの面倒だけ見る
opponent_viewer.py          テストラン。検出器ノード + HTTP のビューア（viz/opponent_view.html）
detector_bench.py           実機で周期・段ごとの時間・検出率を測る CLI
height_probe.py             床の高さ (= カメラ高さ) を検出器に頼らず逆算する CLI
depth_throttle.py           bag 用に depth を間引いて /rec/... へ流す CLI
bag_viewer.py               realsense-viewer の録画 (.bag) を検出器に通してブラウザで見る CLI
rsbag.py                    その .bag (ROS1 形式) を ROS なしで読む
```

依存は numpy だけ。scipy は使っていない。**cv2 は連結成分ラベリングにだけ使い、
無ければ numpy 版に落ちる**（2026-09-23。格子を 2.5 cm にしてここが一番重くなった
ので §10 の 3 番目の手を使った）。切ってあるのは `grid.label_components()` の 1 関数だけ。

## パラメータ

`config/opponent_detector.yaml`。§11 の 3 群に分けてある。

- **`body.*` 機体から決まる** — `cam_height` と `cam_pitch_deg` は**実測して入れること**。
  `cam_height` は高さヒストグラムの窓の中心なので、ここがずれると窓が場外の床を掴む
  方向にずれる。実行時変更は拒否する（姿勢推定の前提そのものなので）
- **`match.*` 競技から決まる** — **クラスタ上端の高さの境界 3 つ**（`obj_top_min` /
  `fallen_top_max` / `robot_top_max`）がここにある。当日会場で追い込むのはこの 3 つ
  （下の「高さの分類を絶対値にする」）。`obj_width_max` は表 2（3 kg 級の腕は軸から
  30 cm）から 0.80 m（§8.3, §12）。bag のミニロボット（上端 26.8 cm・幅 23.2 cm）は
  「その値でミニロボも取れるか」の下限確認にだけ使う
- **`tune.*` 実装から決まる** — 実測で追い込む。`ros2 param set` で実行時に変えられる
  （次フレームから反映。検出器を作り直すので追尾は 1 フレーム切れる）

## Pi 5 での実測（2026-08-28）

§10 と §12 の「Pi 5 での実測をしていない」に対する最初の数字。**合成シーン**
（640×480・約 66,000 点・stride=2）で、実機の bag ではない。

| 測り方 | mean | p95 |
|---|---|---|
| パイプライン単体（`detect` を直接呼ぶ） | 13.9 ms | — |
| ノード経由（`detector_bench`、合成カメラも同じ Pi で動作） | 21.1 ms | 24.5 ms |

30Hz の予算 33 ms には収まっている。`/opponent` は 30.07 Hz で出て、フレーム落ちなし。
CPU は 1 コアの約 82%（Pi 5 は 4 コア）で、これはデバッグ画像を 30Hz で出しながらの値。

段ごとでは `plane`（面あてはめ）が最も重い。あてはめに使う点数の上限
（`tune.fit_max_points=4000`）を入れて 9.8 ms → 1.5 ms に落としてある。1.5 m の
広がりに対して残差 2 mm なら法線は数千点で 0.1° 級に決まるので、全点を使う意味がない。

足りなくなったときの順序は §10 のとおり: `tune.stride` を 3 にする → depth の解像度を
落とす → C++ へ移す。`process_every_n` で処理を間引くこともできる。

### 格子を半分にした（2026-09-23）

`tune.cell` を 0.05 → **0.025 m** にした。これは**判定の解像度そのもの**で、
俯瞰図の粗さもこれ（リング面の連結・崖・塊の足もとが全部この格子の上で決まる）。
848×480・リングを広く写した合成シーンでの全体時間:

| `cell` | 格子 | grid | cluster | 全体 |
|---|---|---|---|---|
| 0.05 | 90×120 | 3.2 | 4.2 | 13.9 ms |
| 0.03 | 150×200 | 4.9 | 5.9 | 18.0 ms |
| **0.025** | 180×240 | 6.1 | 7.5 | **21.5 ms** |
| 0.02 | 225×300 | 3.9 | 9.8 | 22.5 ms |
| 0.015 | 300×400 | 5.6 | 15.3 | 30.8 ms |

そのために 2 つ直した。

- **セル数で効く量を物理量にした。** `intrude_band` [m] / `intrude_min_area` [m²] /
  `bridge_min_area` / `overhead_min_area` / `min_area` / `ring_dilate` /
  `morph_radius` を持ち、`params.py` がいまの `cell` で割る（呼ぶ側は今までどおり
  `*_cells` を読む）。**`cell` だけ変えても帯の幅や塊の最小の広さが動かない。**
  例外は `intrude_cell_points`（飛び画素の話なので点の数のまま。細かくしたら下げる）
- **連結成分を cv2 に逃がした**（§10 の 3 番目の手）。1 フレームに 2 回まわって段の
  中で一番重く、numpy 版で 2.4 + 5.3 ms だったものが 0.5 ms 以下になった。cv2 が
  無ければ numpy 版に落ちるので、**依存としては任意のまま**（numpy 版も union-find の
  Python ループをやめてラベルの伝播に書き直した）

ビューアは俯瞰図を 0.1 秒ごとに生で送るので、1 回 58 KB になった（0.05 のころは 15 KB）。

## まだ確かめていないこと

`docs/opponent_detection.pdf` §12 のうち、この実装で埋まっていないもの:

- **正解ラベルが無い。** 検出率は「何かを出した割合」であって「正しく出した割合」ではない。
  color 画像のマーカー検出で疑似正解を作る案が文書にある
- **実機の bag で回していない。** bag はこのリポジトリに無い。`detector_bench` は
  実機ストリーム向けなので、bag を `ros2 bag play` すればそのまま使える
- **水平付けの実機カメラで回していない。** `body.cam_height` は 0.365 m を実測した
  （2026-09-23）が、`cam_offset_*` は未実測。
  高さの境界（`fallen_top_max` / `robot_top_max`）も、合成シーンと規則の寸法から置いた値で、
  実機の相手機で取り直していない
- **会場の照明とフラッシュの影響を測っていない**
- **相手が 2 台以上見えるときの選択規則**は最近接のまま
